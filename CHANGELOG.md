# Changelog

## Unreleased

### Skills

- **release** — Step 7's "After merge" section now codifies the post-merge duty per `rules/ci-safety.md`'s extended Always Watch CI clause: (1) verify the merge landed on main, (2) **watch the publish workflow to completion** with `gh run watch <run-id> --exit-status` (the previous "check it triggered" wording was fire-and-forget — a silent publish failure would still report success), (3) **verify the new version is live in the registry** with `tessl tile info <workspace>/<tile>` (or the equivalent for non-tile artifacts), (4) report the outcome including registry confirmation. `SCRIPTING.md`'s "Post-merge verification" gate gains the same three-confirmation contract for any `merge-and-cleanup.sh` wrapper. Triggered by repeated cases where the previous "check it triggered" verification scored zero against the actual failure mode — a publish workflow that fails to advance the registry version. If the registry does not show the new version after the publish run returned `success`, that is a CI failure, full stop; the Tessl registry has no moderation queue / hold / rejection state and the rule explicitly forbids inventing one as a plausible explanation.
- **release** — Step 7 now documents the worktree-launched cleanup path alongside the base-checkout one (per the new `rules/agent-worktree-isolation.md`): from inside an additional worktree, the post-merge sequence is `cd` back to base → fast-forward `main` → `git worktree remove <worktree-path>` → `git branch -d <branch>`. Order is mandatory because `git branch -d` refuses to delete a branch checked out in any worktree; reversing produces a "checked out at `<path>`" error and leaves a stranded branch. `SCRIPTING.md`'s Wrapping-Step-7 section gains a corresponding "Worktree-aware teardown" gate so any `merge-and-cleanup.sh` wrapper detects the worktree case (`[ "$(git rev-parse --git-dir)" != "$(git rev-parse --git-common-dir)" ]`) and runs the right teardown sequence instead of surfacing the confusing branch-delete error to the user. Triggered by the surface-composition gap noticed immediately after `agent-worktree-isolation.md` landed on PR #52: the rule mandates worktrees for concurrent agents, but Step 7's cleanup block still assumed the agent was in the base checkout, so following the rule literally produced a broken cleanup.
- **release** — Three quick-fix bundle for Copilot findings on `speaker-toolkit#29`. (a) `#42`: `request-copilot-review.sh`'s `discover_copilot_bot_id` filter matched the bare login `copilot-pull-request-reviewer`, but the GraphQL `Bot.login` is inconsistent — some contexts return the `[bot]`-suffixed form (matching the REST surface), some don't. The filter now accepts either, so the discovery fallback can't silently miss a real Copilot review and run the mutation against an empty actor ID. (b) `#43`: `fetch_pr_node_id`'s `gh api graphql --jq '.data.repository.pullRequest.id'` returned the literal string `null` (with exit code 0) when the PR was missing/invalid; the downstream mutation then ran with `pullRequestId: "null"` and surfaced as a confusing GraphQL error several steps removed from the actual root cause. The function now uses `// empty` to collapse null and refuses with a concrete diagnostic before the mutation can run. (c) `#44`: `GH_AW_DETAILS.md` pinned `claude-opus-4-6` for the Anthropic-side reviewer but the install-reviewer-shipped templates are on `claude-opus-4-7` — the doc was wrong from a consumer's perspective and the dogfood drifted. Replaced the literal model with a pointer to the workflow source's `engine.model` as the single source of truth, so future model bumps land in one place and the doc never goes stale. New `tests/test_request_copilot_review.sh` covers both new code paths (5 tests, all passing): null-PR refusal, real-PR ID return, and bot-login matching with/without/missing the `[bot]` suffix. Tests source the script (the `main()` guard prevents auto-run) and override `gh` with a fixture-driven function so the actual jq filters are exercised end-to-end.
- **install-reviewer** — `preflight.sh` hardened on two fronts. (a) `#40`: jq is required for emitting the script's documented JSON envelope, but the script never checked jq was present — a missing jq produced `jq: command not found` on stderr and no JSON on stdout, leaving the agent with nothing to parse and the install workflow stalling before Step 2 could surface the recovery command. preflight now hand-rolls the missing-jq diagnostic as JSON before any other work, so the failure satisfies the contract the agent depends on (`{"check": "jq-installed", "reason": "...brew install jq...apt install jq..."}`). (b) `#41`: the `branch-not-local` recovery command no longer recommends `git branch -D` (force-delete, destroys unmerged commits silently) — it now recommends `git branch -d` (refuses on unmerged) and offers `git branch -m <branch> <branch>.bak` as a non-destructive alternative; surfacing `-D` to a fresh user running a routine install was a footgun. New `tests/test_preflight.sh` covers the missing-jq path in both install and override modes (asserts JSON validity, exit code, override field, and the OS-specific install hints in the reason).

### Rules

- **plugin-evals** — Coverage section gains a "Narrow exception for closed-loop automated systems with no human eval-result review" carve-out. The structural reasoning: evals are an instrument, not a deliverable; they produce measurements that only become signal when a human (or downstream automated gate that surfaces to a human) reads them and acts. A tile whose entire CI/release/operations loop is fully automated end-to-end, with no eyeballs ever landing on `tessl eval run` output, is generating measurements that never become signal — every eval run is pure cost (Tessl budget, scenario-authoring effort, fixture maintenance) producing zero decisions, and the suite has no theory of how it would catch a regression (real regression manifests → eval flags it → report posts to a workflow log nobody reads → regression ships anyway). Owner-approved 2026-05-09 with `jbaruch/nanoclaw-*` named as the reference example: fully-automated agent loop, no human eval-result review, multi-month observation period confirmed the predicted failure mode (40-scenario suite running on non-gating daily cadence, scenarios were not catching real regressions, several retired for ~zero lift, recurring runs silent on the silent-success regressions they nominally watched for). The condition is narrow and affirmative: a tile must demonstrate no-human-review to claim it; "we don't currently look at the results, but we plan to" does NOT qualify — intent without follow-through is bypass-cope dressed as future-work, the exact framing other rules in this tile (`boy-scout.md`, `context-artifacts.md`'s "Disagreeing With the Reviewer") were authored to close. Tiles that DO have human review — including `coding-policy` itself, where the maintainer reads scenario lift on every publish — are NOT exempt. Pairs with the matching `nanoclaw-admin` PR removing the `evals/` directory and `evals.yml` workflow, which the `review-openai` policy reviewer (correctly) blocked under the previous unconditional rule. Structurally parallel to `dependency-management.md`'s "Narrow exception for runtime-managed manifests" and `error-handling.md`'s "Narrow exception for outer-boundary process contracts" — name, condition, scope, owner approval, reference example.
- **boy-scout** (new) — Adds the Boy Scout Rule as an always-on steering rule: leave the codebase in better shape than you found it; "pre-existing" is not a valid concept; if you see something wrong while doing something else, fix it. The rule's purpose is to close the gate-evasion source — most CI bypass attempts and review-gate evasions ("not my regression", "pre-existing", "out of scope for this PR") share the "I didn't break it so I don't have to fix it" framing; the existing forbid-the-bypass rules (`ci-safety: Never Skip Tests`, `context-artifacts: Disagreeing With the Reviewer`) play whack-a-mole on the exits, this rule rules out the framing. Reconciliation with `commit-conventions: Keep PRs focused`: focus governs the SHAPE of the bundle (one logical change), boy-scout governs whether the agent walks away from problems noticed (no); in-scope cleanups bundle into the current PR, out-of-scope discoveries open follow-up PRs/issues with a reference from the current one — walking away with no record is the failure mode the rule prevents. Triggered by a recurring agent failure pattern observed when publishing skill updates: the `tessl skill review --threshold 85` gate fires on a sibling skill the agent didn't author, and the agent's recommendation flips into one of two forbidden bypass paths ("publish manually from this machine" or "lower the threshold in CI") with the justification that the failure is pre-existing. Both bypass paths are already forbidden; this rule names the underlying reasoning so the policy reviewer can flag the framing in PR bodies and review feedback before the bypass even gets proposed.
- **ci-safety** + **release** (skill + scripting) — Strikes a hallucination this very tile previously planted: the "moderation hold" / "moderation queue" / "moderation rejection" framing in the post-merge registry-verification clauses. **The Tessl registry never rejects a published version.** A failed moderation flag (`moderationPassed: false`) means the version still lands and is fetchable but won't surface in `tessl search`; a security finding means `tessl install` requires an override flag to install — neither is rejection, neither prevents the version from being in the registry. Agents (this one included) kept inventing rejection as a plausible-sounding explanation whenever a registry check failed, instead of reaching the correct diagnosis: "the publish workflow failed; go look at the run." All three live surfaces (`rules/ci-safety.md` "Always Watch CI" extension bullet, `skills/release/SKILL.md` Step 7 third sub-bullet, `skills/release/SCRIPTING.md` Post-merge verification gate) now state the precise capability set explicitly so the hallucination has nowhere to land: registry never rejects, moderation flag affects searchability only, security finding affects install-flag requirements only, registry-not-showing-version-after-CI-success = CI failed. The two prior Unreleased CHANGELOG entries that planted the same wording are also corrected to keep the rule and the changelog from disagreeing. Triggered by direct user feedback after the agent in this conversation kept reaching for the moderation-rejection explanation as a hedge clause across multiple PR cycles — concrete example the user cited: `jbaruch/nanoclaw-trusted 0.1.56` flagged `moderationPassed: false`, with the agent claiming "the registry rejected it" when the bump had in fact landed in both git and the registry; only its searchability was affected.
- **error-handling** — Adds a narrow "outer-boundary process contracts" carve-out to "Specific Exceptions" (#56). Without it, the rule's "no catch-all + let unexpected propagate" clauses produce review-cycle deadlock for precheck scripts and other process boundaries where the caller treats non-zero exit / invalid stdout as a silent-failure signal — letting a programming-bug exception propagate there silently disables the scheduled task, the exact failure mode of the 2026-04-16 → 2026-04-18 outage that `heartbeat-precheck.py` was hardened against. Triggered by the deadlock on `nanoclaw-admin#149` (and predecessor `#139`, merged via override): under the previous 2-bullet rule, the reviewer was correct on both flip-flops — `except Exception:` IS a catch-all, AND a 12-class enumerated `except` list IS broad programming-error trapping; the rule itself was missing the legitimate case. The carve-out matches the structural discipline of `dependency-management.md`'s runtime-managed-manifest exception: name, condition, permitted action with explicit non-permitted form (`except Exception:` only — never `except BaseException:`, which would catch `KeyboardInterrupt`/`SystemExit` and make processes resistant to Ctrl-C / `sys.exit()`), three ANDed preconditions (the literal grep token `outer-boundary-process-contract` always present on the catch line or the comment immediately above it so a single tile-wide grep audits every instance regardless of language, additionally accompanied by the language-native catch-all suppressor on the catch line itself where a linter requires one — Python/Ruff: `# noqa: BLE001` must be inline with the `except Exception:` to suppress BLE001 (placing it on the comment above does not work); rationale comment naming silent-failure shape + contract-keeping emit + propagation-would-break-contract reason; outermost-boundary-only), a "every other catch still specific" reset, and a reference incident. The mandatory `outer-boundary-process-contract` token (always present, in any language, alongside whatever native suppressor the linter requires) makes future instances auditable across consumer codebases via one grep pattern — a plain catch-all is still a violation; only the token-marked form is sanctioned.
- **context-artifacts** — Adds a "Disagreeing With the Reviewer" section codifying the protocol when a skill fails the `tessl skill review --threshold 85` gate. Anti-patterns explicitly forbidden: lowering `--threshold 85` to make the skill pass (the threshold-specific prohibition this section adds); generic CI bypass via local publish, `[skip ci]`, or disabling the review step is already forbidden under `rules/ci-safety.md`'s "Never Skip Tests" — both shift "fix the skill" into "hide the failure" and rot the gate. Correct response when the agent disagrees with the reviewer's conclusions: `tessl skill review --optimize <skill>` run locally after backing up `SKILL.md` and any reference files. The optimized output is a hypothesis, not the answer — the reviewer's judge is not a subject-matter expert and routinely strips load-bearing context the local agent (with project context) knows is necessary. Diff against the backup, keep the genuinely-improving moves (tighter triggers, less prose, better `Skill()` typing), reject the over-aggressive cuts, then re-run the review and iterate. The goal is to learn the reviewer's optimization patterns and re-apply them with subject-matter expertise the judge lacks. Triggered by repeated cases where review-gate failures pushed the agent toward bypass suggestions instead of toward the local-optimize-and-curate workflow that actually fixes the skill. Section also explicitly forbids the "I'll run `--optimize` and ship because the score improved" pattern, which has the same gate-rotting effect as dropping the threshold but disguised as a fix — the score reflects what the rubric measures, not the content the optimizer stripped that the rubric doesn't penalize but the skill's author/local agent knows is load-bearing. Use the optimizer as a diagnostic signal (it surfaces *what kinds* of issues exist — actionability, progressive-disclosure, redundancy) and curate the fixes manually with judgment; never ship its applied output verbatim.
- **ci-safety** — "Always Watch CI" section gains a release-extension bullet: for plugin/tile/package releases, the watch duty extends past merge through the publish workflow AND into registry verification. A merged PR with a green PR-CI but a failed publish workflow is not "shipped"; a green publish workflow with a registry that doesn't have the new version is also a CI failure (the `success` was reported but the registry side didn't actually advance). Either way the diagnosis is "look at the publish run" — the rule explicitly forbids inventing moderation queues, holds, or rejection states (the Tessl registry has none of these), which agents have repeatedly hallucinated as plausible-sounding failure modes. Pairs with the matching Step 7 update in `skills/release/SKILL.md` and the strengthened "Post-merge verification" gate in `skills/release/SCRIPTING.md`.
- **agent-worktree-isolation** — Cleanup section gains a release-skill composition bullet spelling out the post-merge sequence for worktree-launched flows: `cd` back to base, fast-forward `main`, `git worktree remove`, then `git branch -d`. Order is mandatory because `git branch -d` refuses to delete a branch checked out in any worktree. Pairs with the matching Step 7 update in `skills/release/SKILL.md` and the new "Worktree-aware teardown" gate in `skills/release/SCRIPTING.md` — landed in the same PR so the three surfaces stay aligned.
- **agent-worktree-isolation** (new) — Mandates `git worktree`-based isolation any time a task that mutates the repo may run concurrently with another agent on the same checkout. Read-only inspection on the shared checkout is permitted; the moment the task crosses into `Edit`/`Write`/side-effecting `Bash`, the agent must operate in a worktree (the Agent tool's `isolation: "worktree"` parameter is the canonical mechanism for spawned subagents; `git worktree add` covers human-launched parallel sessions). Triggered by repeated cases of multiple concurrent agents racing on the same checkout — branch state, index, working tree, and stash all have last-write-wins semantics, so the agent that "loses" a race produces garbage and reports success. The rule also covers cleanup (`git worktree remove`, never `rm -rf`) and the single-reader exception that evaporates the moment the inspection turns into "let me just fix this one thing." No existing skill in this tile uses `Agent()`-based parallelism on the shared checkout, so no skill changes ride along; the rule applies prospectively to consumer flows where multiple agents share a repo.
- **skill-authoring** — Script References section now distinguishes path-form by audience (#50): repo-relative (`skills/<name>/<file>.<ext>`) for rule prose, documentation, and skill cross-references; the path that resolves at the **invocation site** for step bodies the agent executes — repo-relative when the skill runs from a clone of this repo (e.g., `skills/release/poll-pr-reviews.sh`), the consumer's tile-mount path when the skill runs inside a consumer (e.g., `.tessl/tiles/jbaruch/coding-policy/skills/install-reviewer/preflight.sh`, or whichever absolute path the consumer's runtime documents — `/home/node/.claude/...` is common for hosted-runner mounts). Triggered by `nanoclaw-admin#99`'s script-delegation cleanup epic, where both gh-aw and Copilot reviewers flagged the runtime-absolute paths that the nanoclaw fleet (35+ existing invocations) and nanoclaw's own onboarding doc (`copilot-instructions.md`) treat as the convention; neither reading was wrong, the rule itself was the inconsistency. The previous "Reference scripts with full paths: `scripts/foo.sh`" example was also a third convention distinct from both camps and matched no shipped skill in this tile or the nanoclaw fleet — no skill in coding-policy or nanoclaw places scripts in a `scripts/` subdir; they sit at `skills/<name>/<file>.<ext>` or `<name>/scripts/<file>.<ext>` depending on the tile. Both shipped skills in this tile already exemplified the two-context split before the rule was clarified: `install-reviewer/SKILL.md` uses `.tessl/tiles/...` mount paths because it runs inside a consumer repo, while `release/SKILL.md` uses `skills/release/...` repo-relative paths because it runs from a clone of this repo. The rule update also adds a "don't mix conventions inside one SKILL.md" bullet so authors can't half-migrate a file. No skill changes ride along — the rule now describes what both skills already do; unblocking `nanoclaw-admin#99` is a downstream consequence (the existing 35+ invocations are conformant under the new wording).
- **skill-authoring** — Step Structure clarifies that the "Each step is one action — if a step has an 'and', split it" bullet is a **title heuristic**, not a body-atomization mandate (#39). A step's body MAY list sub-tasks or supporting bullets that all serve one cohesive action; the split signal is two verbs in the H2 title (e.g., "Build and Deploy"), not multiple bullets in the body. Triggered by `jbaruch/speaker-toolkit#27`'s vault-ingress review cycle: across three rounds, the OpenAI reviewer kept finding "another bullet that should have been a step," landing on an 11-step proposal for what is logically a 4-phase batch workflow. The strict body-atomization reading would also retroactively reject `install-reviewer/SKILL.md` Step 4 (scaffold.sh runs cp + compile + .gitattributes update as one atomic operation) and similar steps elsewhere in this tile — a tell that the body-atomization reading isn't the intended rule. Audit confirmed no existing skill in this tile has a step title that combines verbs with "and"/`&`, so no skill changes ride along.
- **skill-authoring** — Title and Preamble + Step Structure sections now explicitly distinguish **sequential workflows** (the default — release / deploy / migrate, "Process steps in order. Do not skip ahead.") from **action routers** (group-management, scheduler-config, anything where the agent picks one of several alternatives by user intent — "This skill is an action router — pick the step that matches the user's intent and execute only that step. Do not run other steps; do not parallelize."). Triggered by the `manage-groups` skill in `nanoclaw-admin#74`: the OpenAI policy reviewer rejected an action-router preamble as conflicting with the rule's literal "force sequential execution" wording, even though the skill is genuinely a router (find / add / remove / list / change-trigger / configure-allowlist / configure-mounts are alternatives, not phases). The previous rule conflated "non-parallelization" with "in-order processing"; routers need the first guarantee but cannot honour the second. Both modes share the same flat-numbered `## Step N` heading format — the difference is the preamble's execution-mode declaration, not the heading shape. Action-router preambles must also be exhaustive on chaining (e.g. "Step 7 is typically chained after Step 3"); the default in routers remains "execute only the chosen step and finish".
- **dependency-management** — "No Vendoring" section gains a Tessl-specific bullet: never commit tile content (e.g., `.tessl/tiles/<workspace>/<tile>/...`) into the consumer repo; install via `tessl install` at runtime. Two failure modes have surfaced on real consumer installs and motivated the explicit prohibition: (1) a vendored copy silently drifts from the registry-published version, so consumers run stale rules without noticing — the rule that's actually loaded into the agent's context is whatever was last committed, not what the registry's `Latest Version` reports; (2) a workspace-local `.tessl/` is wiped by `actions/checkout`'s default `clean: true` in CI runs (the same gap that drove `install-reviewer`'s 0.2.x switch from `--global` install to `/tmp/gh-aw/coding-policy/`), so any reviewer or agent that expects to read tile content out of the workspace finds an empty directory and either fails loudly or — worse — silently runs with no policy loaded. The general "Don't copy library source code into the repo" bullet already covered this in spirit, but consumers were treating tiles as policy artifacts rather than dependencies and committing the install output anyway; the explicit restatement closes that gap. The bullet also points at the install-reviewer changelog entries as the reference incidents so future readers can find the concrete failure modes without re-deriving them.
- **dependency-management** — Adds a narrow exception clause to the Pinning section for runtime-managed manifests: when a tool rewrites a manifest in-place at runtime AND the resolved-version state is gitignored, pin-or-lock produces silent drift between git and the running deployment, so the manifest may use a floating-but-explicit specifier (e.g. `"version": "latest"`) and skip the lock file. The exception is gated on three per-manifest preconditions: (1) the consuming project documents an authority-of-record rule in its own tile naming the carve-out and listing every covered manifest, (2) a deploy-time check fails the deployment if any disallowed specifier (literal pin, range, tag, or anything other than the permitted floating specifier) appears in that manifest, (3) each covered manifest is named explicitly in the authority-of-record rule. Multiple named manifests are permitted iff each independently satisfies all three preconditions; the carve-out doesn't widen to "any manifest" and doesn't apply transitively. Triggered by two NanoClaw incidents: `tessl-workspace/tessl.json` accumulated a 22-day silent drift on 2026-04-27 because `tessl update` rewrites the manifest in-place; the same `tessl update` invocation also rewrites the project-root `tessl.json` (a separate manifest `tessl install` consumes to populate gitignored `.tessl/tiles/` for `@.tessl/RULES.md` resolution at agent runtime), which accumulated silent `vendored`-mode + pin drift on 2026-05-03. Both manifests are now covered by the same authority-of-record rule (`nanoclaw-host: tessl-version-floating`) with one combined `scripts/deploy.sh` walk-and-verify check. The deploy-time gate's specifier-rejection scope was broadened from "literal pin" to "any disallowed specifier" — rejecting only literal pins lets a non-literal pinned/ranged value slip through while still violating the carve-out's intent. Surfaced by the gh-aw OpenAI policy reviewer's `CHANGES_REQUESTED` on `jbaruch/nanoclaw#485` against the unbroadened single-manifest wording, plus Copilot review on closed PR #61 against the deploy-time gate's specifier scope. Companion PRs: `jbaruch/nanoclaw#485` (flips project-root `tessl.json` to `mode: "managed"` + `version: "latest"`, broadens `scripts/deploy.sh` step 3b to walk every `tessl.json`); `jbaruch/nanoclaw-host#18` (broadens authority-of-record rule to cover both manifests).

## 0.3.0

Second formal minor since 0.1.0 — `install-reviewer` gains an in-place upgrade path (`--override`) so consumers no longer have to manually `git rm` four files (or hand-backport fixes, defeating the managed-scaffold contract) every time a fix lands in this changelog. The skill description's "Use when..." clause now lists upgrade trigger phrases (`upgrade`, `update`, `refresh`, `pull latest reviewer templates`, `override`); each of the five scripts (`preflight.sh`, `branch.sh`, `scaffold.sh`, `commit.sh`, `push.sh`) accepts `--override` and emits an `override: bool` field in its JSON output. Step 3's branch-selection logic moved out of SKILL.md prose into a new `branch.sh` script per `rules/script-delegation.md` (deterministic operations belong in scripts, not embedded decision trees the agent reproduces) and `rules/skill-authoring.md` (flat one-action steps, no sub-step bullets).

### Skills

- **install-reviewer** — Added `--override` flag for upgrading existing scaffolded reviewer files in place (#35). Without `--override`, the skill runs in install mode (current behavior; Step 2 refuses if any of the four target files exist). With `--override`, the skill switches to upgrade mode: a different feature branch (`feat/upgrade-coding-policy-review`), a different commit message and PR title (`ci(review): upgrade ...`), preflight skips the branch-clear checks (the upgrade branch may legitimately already exist from a prior in-flight upgrade attempt) and instead refuses if any of the four target files have uncommitted local edits — mirrors how `git pull` refuses to overwrite a dirty working tree, forces the consumer to commit/stash before the scaffold replaces their files; scaffold snapshots ALL four target files (sources + locks) before the cp/compile and restores them on compile failure (extending the existing `actions-lock.json` snapshot+rollback contract); commit/push pick the upgrade branch automatically. Each of the five scripts (`preflight.sh`, `branch.sh`, `scaffold.sh`, `commit.sh`, `push.sh`) accepts `--override` as a positional argument (parsing is order-independent across `$@`) and emits an `override: bool` field in its JSON output so callers can verify the mode they're running under. Step 3's branch-selection logic moved out of SKILL.md prose into the new `branch.sh` script per `rules/script-delegation.md` (deterministic operations belong in scripts, not embedded decision trees the agent reproduces) and `rules/skill-authoring.md` (flat one-action steps, no sub-step bullets) — Step 3 now invokes `branch.sh` and the install-vs-upgrade branch dispatch lives in one place. SKILL.md adds a "two modes" preamble plus per-step bash blocks showing both invocations; the description's "Use when..." clause now lists upgrade trigger phrases (`upgrade`, `update`, `refresh`, `pull latest reviewer templates`, `override`). Fixes the unblocking pain consumers had on every prior fix in this changelog: today the only options were manually `git rm`-ing four files, hand-backporting fixes (defeating the managed-scaffold contract), or accumulating drift.
- **install-reviewer** — OpenAI reviewer prompt now treats the PR's changed-files list as a closed allowlist for inline-comment paths (#32). Codex was hallucinating inline-comment paths outside the PR diff (e.g., posting on `tile.json:3` when the diff only touched `.github/workflows/*`); GitHub rejected the resulting `create_pull_request_review_comment` calls with HTTP 422 ("Path could not be resolved"), which cascade-failed the subsequent `submit_pull_request_review` so the substantive verdict never landed on the consumer's PR. The workflow's safe-outputs handler caught the API error gracefully — masking the failure as a green run with no review posted. Hard fix: Step 3 now explicitly extracts `CHANGED_FILES` from `gh pr view --json files`; Step 5 instructs the agent to validate `path` against `CHANGED_FILES` before each `create_pull_request_review_comment` call (drop the inline comment and fold the finding into the review body if the path doesn't match); Guardrails restate the constraint with the concrete failure mode (422 → cascade-fail). Same change mirrored in the dogfood `.github/workflows/review-openai.md`. Anthropic-side reviewer not affected (Claude wasn't observed hallucinating paths), but the same `CHANGED_FILES` allowlist could be added defensively if the failure mode ever appears there.
- **install-reviewer** — Three quick-fix bundle for issues surfaced from real consumer installs (#30, #33, #34). (a) `scaffold.sh` post-compile sanitization extended: in addition to stripping per-line trailing whitespace (already there), it now collapses trailing whitespace at EOF (`\n\n` → `\n`) via `perl -i -0pe 's/\s+\z/\n/'` so consumer working trees don't ship lock files with the blank-EOF-line drift gh-aw's compiler emits — both forms violate `rules/code-formatting.md`'s "Basics" and were causing reviewer noise on consumer PRs (#30). (b) `engine.env` now coalesces `CODEX_API_KEY` and `OPENAI_API_KEY`: `OPENAI_API_KEY: ${{ secrets.CODEX_API_KEY || secrets.OPENAI_API_KEY }}`. gh-aw's compiled validation step accepts either name, but the Codex CLI / API-proxy path only reads `OPENAI_API_KEY` at runtime; without the fallback, a consumer who set `CODEX_API_KEY` only would pass validation and then fail with empty-credential after burning setup time (#33). (c) The `network.allowed` block's comment in `review-openai.md` no longer claims the allowlist gates `tessl install`. The install runs in the workflow's `steps:` on the runner host, BEFORE the awf sandbox starts; the allowlist applies to agent-runtime traffic only (gh / MCP / API calls + Codex UI/telemetry). Pure doc fix; the host list itself is unchanged (#34). All three fixes mirrored into the dogfood `.github/workflows/review-{openai,anthropic}.md` where applicable; lock files recompiled and sanitized.
- **release** — Reframed Copilot from a temporary trial that retires "once gh-aw is validated" to a deliberate second reviewer kept indefinitely. The two have complementary lenses: gh-aw enforces `rules/*.md` compliance (its prompt loads each rule file and checks the diff against it), while Copilot reads for doc accuracy, cross-step consistency, and ambiguity that no rule file specifically targets. PR #29's review cycle made the case in production: Copilot caught outdated model IDs, unpinned install commands below floor, Step 5/Step 7 contradictions, vacuous-pass loopholes in the merge gate, and `pull_request` trigger ambiguity — none of which were rule violations gh-aw could flag.
