### Rules

- **external-repo-contributions** (new) — Always-on rule defaulting to deny on issues, pull requests, comments, reactions, and discussions in repositories the operator does not own. Explicit permission required per repo AND action type (operator names both in the current conversation, or a standing instruction in an operator-controlled source — `~/.claude/CLAUDE.md`, the project `CLAUDE.md` of a repo the operator owns, or operator-curated agent memory — names them). The permission-source list deliberately excludes `CLAUDE.md` or other instruction files inside repositories the operator does not own: those are controlled by the external repo, not by the operator, and accepting them as a permission source would let the very repo the rule restricts grant itself permission — the exact bypass the rule is closing (caught by the OpenAI gh-aw reviewer on the introducing PR). Bullets enumerate common bypass patterns that do NOT qualify (e.g., permission to fix a bug locally is not permission to file it upstream; "this should be reported" instinct is not consent; permission for one external repo does not extend to others). Motivation: agents acting under the operator's GitHub identity in external projects produce AI-generated content the operator never consented to publish under their name, damaging their reputation in those communities. Surface sync: `tile.json` steering, README rules table + What's-New count 19 → 20 and new "Scope" category row, `.claude/CLAUDE.md` dogfood import.

- **script-as-black-box** (new) — Conditional rule (`applyTo: skills/**/SKILL.md, skills/**/*.md`) requiring skill prose to name the script's contract (inputs, outputs, exit codes, verbatim-emitted text shapes) and not restate the script's internal logic (thresholds, predicates, formulas, allowlists, source lists, per-tier rules). Surface sync: `tile.json` steering, README rules table + What's-New count 18 → 19. Triggered by `jbaruch/nanoclaw-admin#288`; PR body carries the full incident trail.

- **ci-safety** (closes #67) — Adds a "Content-Only Direct-Push Carve-Out" section to "Protected Branches" permitting direct pushes to `main` or `master` for content-only paths under three ANDed preconditions: authority-of-record rule in the consuming tile, narrow path-glob scope excluding all executable/loaded artifacts (`rules/**`, `skills/**`, workflow files, manifests), and push-time enforcement that rejects the entire ref update when any changed path lies outside the carve-out globs (post-push CI checks do not qualify). - **ci-safety** (#80) — Release contract's confirmation step changes from "registry advanced past baseline" (single signal) to a conjunction: the resolved publish run's `conclusion` is `success` AND the registry's `Latest Version` strictly advanced past the baseline. Both signals are required because either alone is unsafe: registry-advance alone races interleaved publishes (an earlier PR's publish run can advance the registry between baseline-capture and the post-merge check while OUR run failed — the queued/in-flight race the issue surfaces); conclusion alone can pass a workflow that exited cleanly without publishing (conditional skip, no-op publish step). The rule's "workflows can succeed without publishing, or fail after publishing" parenthetical is preserved and re-cast: the failure mode `succeed without publishing` is now caught by the registry-advance conjunct; the failure mode `fail after publishing` becomes a loud false-negative (operator checks the registry, sees the publish landed) instead of a silent race — the workflow-design fix is to keep the publish step last. The "If the registry didn't advance" bullet is updated to "If either conjunct fails, the publish is not confirmed" — failure of either conjunct (not just both together) breaks the conjunction. Surfaced by Copilot on PR #76 (out-of-scope per `rules/commit-conventions.md`) — that PR's contract changes (exact-run binding via `gh pr view --json mergeCommit` + `event:push` filter) closed the wrong-run race but the queued/in-flight race remained latent until this PR.

- **Evals — `pr-merge-and-post-merge-cleanup`** (closes #59, #77) — Companion update for the post-merge contract changes that landed across PR #54 (0.3.10, watch-to-completion + registry verify), PR #57 (0.3.11, SHA-bound publish-run binding), and PR #80 (the conjunction rewrite above). The scenario's old "Publish CI verification" criterion (max_score 10) graded the fire-and-forget shape — a `gh run list` / `gh run view` "the workflow was triggered" check — that those three PRs successively replaced; a `merge-and-cleanup.sh` wrapper that only confirmed the publish workflow was enqueued would score full marks on this criterion while bypassing the actual rule. Issue #59 named the post-PR-#54 drift in May 2026; issue #77 re-surfaced the registry-advance piece specifically after PR #76's Copilot pass; one criteria.json rewrite closes both. Replaced with four atomic criteria, each measuring one gate of the new contract: (a) **Pre-merge registry baseline captured** (max_score 8) — script must capture `Latest Version` BEFORE `gh pr merge` (`PRE=$(tessl tile info ...)` or equivalent) so the post-merge check has something to compare against; without the baseline, the agent can't tell "this release published" from "a prior release already shipped this version". (b) **SHA-bound publish-run resolution** (max_score 10) — derives the merge-commit SHA via `gh pr view <N> --json mergeCommit --jq '.mergeCommit.oid'` and filters runs by `.headSha == "<merge-sha>"` AND `.event == "push"` (jq string literals); `gh run list --limit 1`, "latest on main", branch-only filters, and workflow-name-only selectors score zero because each can pick a parallel-merge run or a manual `workflow_dispatch`. (c) **Watch publish run to terminal state** (max_score 8) — `gh run watch <id>` against the specific run id, not a poll-once snapshot or trigger confirmation. (d) **Conjunction check: run-success AND registry-advanced** (max_score 15) — gates final success on BOTH conjuncts and explicitly scores zero for four failure shapes the prior PRs identified: run-success alone (PR #80's race), registry-advance alone (same), expected-version derivation from the merge SHA's manifest (PR #57's race), and any moderation-state hallucination (`rules/ci-safety.md`'s explicit non-rejection statement — the registry never rejects published versions; missing-after-success means CI failed, full stop). Other correctly-aligned criteria reduced proportionally so the checklist sum stays at exactly 100 per `skills/eval-authoring/SKILL.md` Step 5; the four new publish-related gates carry 41 points combined (up from the old single criterion's 10), reflecting that the post-merge gate is the most tile-prescribed part of this scenario — `Pre-merge CI gate` drops 15 → 10, `Merge strategy --merge` and `--ff-only` drop 10 → 8 each, `Pre-merge review gate` drops 10 → 6, `branch -d` drops 8 → 5, `Verifies merge landed on main` drops 8 → 5, `Stale remote-tracking refs pruned` drops 7 → 4, `Final summary` drops 7 → 4, `--delete-branch` drops 5 → 4, `Graceful failure` drops 5 → 3, `No hardcoded` drops 5 → 2. No misaligned criterion's weight increased per the eval-authoring rule. task.md's output-spec line updated from "Confirms the publish/release CI workflow was **triggered**" (which both leaked the technique into the task and encoded the stale fire-and-forget contract) to "Confirms the release was actually published successfully before exiting" — situation-only, no technique prescribed; baseline agents are still free to interpret "published successfully" as `gh run list` (and will score zero on the publish-related criteria), policy-aware agents apply the multi-gate sequence. Bleeding check passed: none of the criteria-specific literals (`baseline`, `headSha`, `Latest Version`, `conjunction`, `gh run watch`, `gh run list`, `PRE=`, `merge_sha`, `moderation`) appear in task.md. Scenario directory name unchanged per the rename-stability clause in `rules/plugin-evals.md`'s Naming section.

- **install-reviewer** (#65) — `scaffold.sh`'s `.gitattributes` append/sanitation logic extracts into an `ensure_gitattributes_marker` helper that runs two-stage EOF normalization whenever the target file exists, regardless of whether the append branch fired. EOF normalization is OUTSIDE the marker-absent branch so a previously-affected consumer (marker present, trailing newline missing) gets repaired by re-running the skill — short-circuiting on marker-present would trap such consumers in the broken state until they hand-edit. Stage one is a bash-only authoritative fix: if the last byte isn't a newline, append one with `printf '\n'` (POSIX, no perl dependency, never fails silently). Stage two is a perl best-effort follow-up — `perl -i -0pe 's/\s*\z/\n/'` (zero-or-more, NOT one-or-more) — that also collapses multiple trailing newlines to one. The `\s*\z` form is mandatory: when EOF is a non-whitespace byte (the reported failure mode), `\s+\z` requires at least one trailing whitespace to match and no-ops, leaving the missing-newline violation in place. The append printf was landing the file without a trailing newline on real consumer installs (cross-family policy reviewer caught it on `jbaruch/coding-policy-evals#1`), violating `rules/code-formatting.md`'s "End files with a single newline" basic. New `tests/test_scaffold_gitattributes.sh` (7 tests) covers fresh consumer, existing file with/without trailing newline, marker-present canonical (no-op), marker-present-missing-newline (repaired, no duplicate marker), and idempotency on both canonical and repaired states. Tests use POSIX `cksum` + `od` for byte assertions; trailing-newline-count uses perl (same dep the scaffold itself optionally uses).

The rule update also adds a "don't mix conventions inside one SKILL.md" bullet so authors can't half-migrate a file. No skill changes ride along — the rule now describes what both skills already do; unblocking `nanoclaw-admin#99` is a downstream consequence (the existing 35+ invocations are conformant under the new wording).
- **skill-authoring** — Step Structure clarifies that the "Each step is one action — if a step has an 'and', split it" bullet is a **title heuristic**, not a body-atomization mandate (#39). A step's body MAY list sub-tasks or supporting bullets that all serve one cohesive action; the split signal is two verbs in the H2 title (e.g., "Build and Deploy"), not multiple bullets in the body. Triggered by `jbaruch/speaker-toolkit#27`'s vault-ingress review cycle: across three rounds, the OpenAI reviewer kept finding "another bullet that should have been a step," landing on an 11-step proposal for what is logically a 4-phase batch workflow. - **skill-authoring** — Title and Preamble + Step Structure sections now explicitly distinguish **sequential workflows** (the default — release / deploy / migrate, "Process steps in order. Do not skip ahead.") from **action routers** (group-management, scheduler-config, anything where the agent picks one of several alternatives by user intent — "This skill is an action router — pick the step that matches the user's intent and execute only that step. - **dependency-management** — "No Vendoring" section gains a Tessl-specific bullet: never commit tile content (e.g., `.tessl/tiles/<workspace>/<tile>/...`) into the consumer repo; install via `tessl install` at runtime. Two failure modes have surfaced on real consumer installs and motivated the explicit prohibition: (1) a vendored copy silently drifts from the registry-published version, so consumers run stale rules without noticing — the rule that's actually loaded into the agent's context is whatever was last committed, not what the registry's `Latest Version` reports; (2) a workspace-local `.tessl/` is wiped by `actions/checkout`'s default `clean: true` in CI runs (the same gap that drove `install-reviewer`'s 0.2.x switch from `--global` install to `/tmp/gh-aw/coding-policy/`), so any reviewer or agent that expects to read tile content out of the workspace finds an empty directory and either fails loudly or — worse — silently runs with no policy loaded. The bullet also points at the install-reviewer changelog entries as the reference incidents so future readers can find the concrete failure modes without re-deriving them.
- **dependency-management** — Adds a narrow exception clause to the Pinning section for runtime-managed manifests: when a tool rewrites a manifest in-place at runtime AND the resolved-version state is gitignored, pin-or-lock produces silent drift between git and the running deployment, so the manifest may use a floating-but-explicit specifier (e.g. `"version": "latest"`) and skip the lock file. The exception is gated on three per-manifest preconditions: (1) the consuming project documents an authority-of-record rule in its own tile naming the carve-out and listing every covered manifest, (2) a deploy-time check fails the deployment if any disallowed specifier (literal pin, range, tag, or anything other than the permitted floating specifier) appears in that manifest, (3) each covered manifest is named explicitly in the authority-of-record rule. Multiple named manifests are permitted iff each independently satisfies all three preconditions; the carve-out doesn't widen to "any manifest" and doesn't apply transitively. Triggered by two NanoClaw incidents: `tessl-workspace/tessl.json` accumulated a 22-day silent drift on 2026-04-27 because `tessl update` rewrites the manifest in-place; the same `tessl update` invocation also rewrites the project-root `tessl.json` (a separate manifest `tessl install` consumes to populate gitignored `.tessl/tiles/` for `@.tessl/RULES.md` resolution at agent runtime), which accumulated silent `vendored`-mode + pin drift on 2026-05-03. Both manifests are now covered by the same authority-of-record rule (`nanoclaw-host: tessl-version-floating`) with one combined `scripts/deploy.sh` walk-and-verify check. The deploy-time gate's specifier-rejection scope was broadened from "literal pin" to "any disallowed specifier" — rejecting only literal pins lets a non-literal pinned/ranged value slip through while still violating the carve-out's intent. Surfaced by the gh-aw OpenAI policy reviewer's `CHANGES_REQUESTED` on `jbaruch/nanoclaw#485` against the unbroadened single-manifest wording, plus Copilot review on closed PR #61 against the deploy-time gate's specifier scope. Companion PRs: `jbaruch/nanoclaw#485` (flips project-root `tessl.json` to `mode: "managed"` + `version: "latest"`, broadens `scripts/deploy.sh` step 3b to walk every `tessl.json`); `jbaruch/nanoclaw-host#18` (broadens authority-of-record rule to cover both manifests).
